## Decision 1: Kernel Sandboxing via gVisor (`runsc`) & Strict RAM Clamping (VULN-03)

### Decision
Confine all untrusted code execution, unit test execution, and arbitrary shell commands generated by `ZeroClaw` inside Kubernetes pods governed by the gVisor (`runsc`) user-space kernel runtime.
- **Application Container Limits**: Bounded strictly to $\le 30\text{ MiB}$ RAM and $\le 250\text{m}$ CPU.
- **Sidecar Container Limits**: OpenZiti mTLS sidecars (`ziti-edge-tunnel`) explicit bounds of $\le 20\text{ MiB}$ RAM and $\le 100\text{m}$ CPU in Kubernetes GitOps manifests.
- **Forensic RAM Hygiene**: All ephemeral credentials, signing keys, and session tokens derive `#[derive(Zeroize, ZeroizeOnDrop)]` ensuring instant overwrite with null bytes in $< 4.33\,\mu\text{s}$ (benchmarked down to $0.045\,\mu\text{s}$).

### Rationale
- Standard Docker/container runtimes share the host kernel. An agent executing untrusted or adversarial code could exploit kernel vulnerabilities to achieve host escape. gVisor intercepts system calls in user space, mitigating container breakouts.
- Clamping application RAM to $30\text{ MiB}$ eliminates memory exhaustion, crypto-mining, and local resource exhaustion attacks.
- Setting explicit memory limits on the OpenZiti sidecar eliminates premature `OOMKilled` eviction of the primary container.

### Alternatives Considered
- **Bare Host Execution**: Rejected due to zero isolation and catastrophic host exposure.
- **Standard runc / Containerd**: Rejected because container escapes via shared Linux kernel syscalls violate Zero-Trust standards.
- **Firecracker MicroVMs**: Evaluated as viable, but gVisor provides lighter startup latency ($\approx 150\text{ms}$) and integrates seamlessly with existing Kubernetes `RuntimeClass` and Cilium CNIs.

## Decision 2: Dark Network Overlay (OpenZiti mTLS 1.3) & Outbound-Only Polling

### Decision
Eliminate all public ingress ports, NodePorts, and inbound HTTP webhooks on the autonomous factory perimeter.
- All inter-agent and inter-service communication (Agents $\leftrightarrow$ Kafka $\leftrightarrow$ LiteLLM $\leftrightarrow$ R2R vector DB $\leftrightarrow$ Vault) operates over **OpenZiti mTLS 1.3 encrypted overlay tunnels**.
- External VCS interaction (GitLab/GitHub) operates exclusively via outbound polling (`GitPlatformPoller` / `factory-cli poller`) every 30–60 seconds.
- Long-term transition from sidecar processes (`ziti-edge-tunnel`) to native Rust crate `openziti-rs` / FFI inside `crates/factory-infrastructure/src/ziti.rs`.

### Rationale
- Inbound webhooks require internet-facing endpoints susceptible to DDoS, unauthenticated payload flooding, and SSRF attacks.
- OpenZiti makes services completely dark to public port scans while providing mutual TLS identity attestation at layer 4/7.
- Embedding native mTLS in Rust reduces pod footprint by eliminating sidecar memory overhead entirely.

### Alternatives Considered
- **Public Ingress with Reverse Proxy & WAF**: Rejected because open ports remain discoverable and vulnerable to perimeter zero-days.
- **WireGuard / IPSec VPN**: Rejected due to static network topology and inability to enforce granular zero-trust application-level identities per agent.

## Decision 3: Non-Human Identities (NHI) & Ephemeral Vault JIT Tokens (VULN-04)

### Decision
Assign each autonomous agent (Rustant, ZeroClaw, DevOps, Documentation) an immutable Non-Human Identity (NHI) backed by Ed25519 cryptographic key pairs managed in HashiCorp Vault.
- Vault paths are isolated per repository and agent (`secret/data/repos/<repo>/*`).
- Access tokens (Git, S3, cluster) are issued Just-In-Time (JIT) with a non-renewable, strict TTL of 5 minutes (300 seconds).
- All Git commits, database entries, and agent-to-agent operations emit W3C Verifiable Credentials signed via `ed25519-dalek` v2 (`Ed25519Signature2020` / JWS).

### Rationale
- Fulfills EU AI Act (Art. 14, 15) and SOC 2 Type II non-repudiation and causal traceability requirements.
- The 5-minute TTL guarantees that compromised or leaked tokens self-expire before external misuse can occur.
- Vault isolation prevents lateral privilege escalation across repository boundaries.

### Alternatives Considered
- **Static API Keys in Kubernetes Secrets**: Rejected due to high risk of secret proliferation, lack of rotation, and shared accountability.
- **OIDC Long-Lived Service Accounts**: Rejected because tokens lasting $> 1\text{ hour}$ represent an unacceptably wide window of vulnerability.

## Decision 4: Adaptive Velocity Circuit Breaker & Heterogeneous SAST Review (VULN-01 & VULN-02)

### Decision
Upgrade the Aethelgard verification gate and `CircuitBreakerGuard` with temporal velocity awareness, diff-hash deadlock detection, and heterogeneous model separation:
1. **Model Diversity**: LiteLLM Gateway routes `ZeroClaw` code generation to local high-throughput models (`Bonsai 27B Ternario` or `Qwen 2.5 Coder 7B`), while the SAST judge (`security_review`) is routed to an independent, architecturally separate frontier model family (or Azure AI Foundry tunnel). Minimum score threshold $\ge 8.0 / 10.0$.
2. **Deadlock Detection**: Computes SHA-256 hashes of generated code diffs across consecutive attempts; if identical hashes are produced, the circuit breaker opens immediately on attempt 2 rather than burning all 3 attempts.
3. **Spend Velocity Tripping**: `FinOpsAgent` queries `/spend/logs` every 60 seconds; if spend acceleration exceeds $+\$1.00 / 60\text{s}$, a velocity anomaly is flagged.
4. **Execution Freeze**: Upon 3 failures, deadlock detection, or velocity breach, the Hatchet DAG is frozen, active JIT tokens are revoked, mission status becomes `Agent-Stuck`, and a structured alert is dispatched to the human architect (HITL Vertex 3).

### Rationale
- Resolves VULN-01 (Temporal Asymmetry) where machine-speed retries burn budgets in seconds before human reaction.
- Resolves VULN-02 (Model Bias in SAST Judge) where homogenous evaluators miss self-generated backdoors or logic bugs.
- Prevents infinite reasoning loops and diff regeneration cycles.

### Alternatives Considered
- **Single Model for Both Generation & Review**: Rejected due to demonstrable self-confirmation bias in LLM evaluators.
- **Static 3-Retry Counter Without Velocity or Hash Checks**: Rejected because agents can cycle through 3 retries in under 5 seconds with zero variation in diff output.

## Decision 5: FinOps Virtual Tags (`Vtags`) & HardStop Guardrails (VULN-05)

### Decision
Enforce real-time cost attribution and hard cut-off guardrails through the LiteLLM Gateway and `FinOpsAgent`:
- Metadata structure `FinOpsTag` (`team`, `epic`, `microservice`, `environment`, `cost_center`) is injected into all HTTP inference requests:
  - `x-vtags-team: dark-gravity-ops`
  - `x-vtags-epic: <epic_id>`
  - `x-vtags-microservice: factory-application`
  - `x-vtags-cost_center: eu-rd-grants`
- Default daily budget is parameterized via `FINOPS_MAX_DAILY_BUDGET` (default: $\$50.00\text{ USD}$).
- When cumulative mission spend reaches $90\%$ of daily budget ($\$45.00$), a `HardStop` cutoff halts all active inference, publishes a `budget-exceeded` event on Kafka, revokes active JIT credentials, and halts execution.

### Rationale
- Mitigates VULN-05 (Denial of Wallet / Prompt Injections driving infinite chain-of-thought loops).
- Enables exact granular financial auditing per epic and microservice.

### Alternatives Considered
- **Monthly Billing Alerts**: Rejected because cloud provider billing alerts have a 24–48 hour delay, during which a runaway agent can run up thousands of dollars in inference costs.
- **Total Request Count Limits**: Rejected because token pricing varies widely between prompt caching, context length, and completion tokens.

## Decision 6: Asynchronous Batch Cryptographic Signing Pipeline

### Decision
Implement non-blocking asynchronous signing and verification queues using Tokio tasks (`sign_async` and `sign_batch_async`) powered by `ed25519-dalek` v2.

### Rationale
- Synchronous cryptographic signing on the main async event loop induces CPU starvation and latency spikes during high-frequency Agent-to-Agent (A2A) message exchanges.
- `sign_batch_async` leverages `tokio::task::spawn_blocking` to distribute Ed25519 signature computation across threadpools while maintaining $> 100\text{ ops/sec}$ throughput.

### Alternatives Considered
- **Synchronous In-Line Signing**: Rejected due to latency degradation in high-volume Kafka streaming.
- **Asymmetric RSA-4096**: Rejected due to excessive signature size and heavy compute overhead compared to compact 64-byte Ed25519 signatures.
