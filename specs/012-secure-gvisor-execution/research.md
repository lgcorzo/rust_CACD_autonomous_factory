# Research & Decision Record: Secure gVisor Execution & Evidence Governance

**Feature**: `012-secure-gvisor-execution`
**Date**: 2026-11-08

## 1. Zero-Trust Sandboxing: Eliminating Host Subprocess Fallback for Untrusted Code

### Context & Problem
In `crates/factory-mcp-server/src/lib.rs` and `sandbox.rs`, if `SANDBOX_MODE` is not explicitly set to `"gvisork8s"`, the system defaults to `SubprocessDriver::new()`. Furthermore, in non-production environments (`APP_ENV != "production"`), `SubprocessDriver` allows execution directly on the host machine. This violates the zero-trust isolation requirement (DG-RVP-001) for all untrusted code generated by agents.

### Decision
1. **Remove implicit subprocess fallback**: In `crates/factory-mcp-server/src/lib.rs`, `GvisorK8sDriver` must be the default driver for all untrusted code execution.
2. **Explicit Secure Driver Selection**: If `SANDBOX_MODE` is unset or invalid, default strictly to `GvisorK8sDriver` (or an explicit Kubernetes secure container driver).
3. **Hard Fail-Closed Policy**: If `SubprocessDriver` is ever called for untrusted code execution (even in development), it must strictly reject execution with an `InfrastructureError` / `PermissionDenied` unless an explicit, developer-override flag (`ALLOW_INSECURE_HOST_EXECUTION=true`) is explicitly passed AND the environment is local testing (prohibited in cluster/dev/staging/production).
4. **Recording Driver Scoping**: Ensure `RecordingSandboxDriver` is only used in isolated unit test harnesses for interface testing, and clear markers distinguish mock tests from live end-to-end sandbox attestation.

### Alternatives Considered
- *Allowing Subprocess in dev with a warning log*: Rejected because development clusters and local agent runs can still be compromised by malicious code escapes or destructive operations on the host filesystem.
- *WASM/Wasi sandbox*: Good for lightweight execution, but does not support compiling multi-crate Rust projects or full Cargo test runs with GCC/ld linkers.

## 2. Containerd Runsc Shim & MicroK8s RuntimeClass Integration

### Context & Problem
Audit AUD-010 noted that the containerd shim on `server.internal.lgcorzo` previously defaulted to `io.containerd.runc.v2` instead of `io.containerd.runsc.v1`, preventing pods configured with `runtimeClassName: gvisor` from starting properly.

### Decision
1. **Containerd Configuration**: Ensure the MicroK8s containerd configuration (`/var/snap/microk8s/current/args/containerd-template.toml`) registers `runsc` under plugins:
   ```toml
   [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runsc]
     runtime_type = "io.containerd.runsc.v1"
   ```
2. **RuntimeClass**: Ensure Kubernetes `RuntimeClass` named `gvisor` with handler `runsc` exists in the cluster.
3. **Sandbox Pod PodSpec**: In `crates/factory-mcp-server/src/tools/launch_sandbox_pod.rs`, ensure `runtimeClassName: Some("gvisor".to_string())` is applied to sandbox pods when gVisor is enabled, backed by immutable image digests, non-root security context, dropped capabilities, and 512Mi memory limits.

## 3. Distributed Atomic FinOps Storage

### Context & Problem
The current FinOps stop store (`FileFinOpsStopStore`) utilizes a process-local PID in its default path and relies on in-memory `std::sync::Mutex`, which does not guarantee atomic coordination or cross-process serialization across multiple worker replicas (`factory-worker-XXXXX` and `factory-worker-YYYYY`).

### Decision
1. **File-Level Advisory Lock / Shared Persistent Store**: For filesystem-based persistent stores, implement advisory file locking (`fs2` or POSIX `flock` / atomic tempfile rename) so concurrent worker processes serialize reads and mutations to `finops_stops.json`.
2. **Shared Mount / Centralized Backend**: Support persistent path pointing to a Kubernetes `ReadWriteMany` PVC or shared cluster mount (`FINOPS_STOP_STORE_PATH`), or database-backed state store (PostgreSQL/Redis) with compare-and-swap (CAS) transactions.
3. **Fail-Closed on Locking Failure**: If the file lock or backend cannot be acquired within a timeout, admission queries must fail-closed to prevent budget overruns.

## 4. Evidence Gate Freshness & SHA Invalidation

### Context & Problem
Evidence generated in previous audit cycles referenced commit `1b9a51f8`, which is now stale compared to current `HEAD` (`a71d000` / `aef999a1`). Furthermore, the Evidence Gate must explicitly distinguish synthetic/mock driver executions from true containerized gVisor executions.

### Decision
1. **Commit Freshness Check**: `factory-cli validate-evidence` must verify that the evidence target commit SHA matches current `HEAD` (or the exact commit being evaluated in the PR pipeline). If `evidence.commit_sha != target_sha`, the gate must fail with `EVIDENCE_STALE_COMMIT`.
2. **Execution Environment Attestation**: Add an `attestation` / `environment` field in the verification evidence schema (`sandbox-gvisor-k8s`, `sandbox-container`, `mock-recording`). Production and PR gates must reject evidence bearing `mock-*` or `subprocess-insecure` execution attestations for Verified Autonomous Execution claims.
3. **Timestamp Expiration**: Set an evidence freshness TTL (e.g. 24 hours). Evidence older than the TTL requires re-execution.
